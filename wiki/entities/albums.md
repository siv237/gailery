# Альбомы

**Сущность:** фотоальбомы — ручные (собираются пользователем из «семечек») и авто
(генерируются кластеризацией по времени, gap ≤ 2ч, ≥ 5 фото).

Код: `src/api/albums.py` (API), `src/database.py` (методы `*_album*`),
`web/albums.html` (страница альбомов), `web/catalog.html` (кнопка «В альбом»).

## Хранилище

| Таблица | Что хранит |
|---|---|
| `albums` | album_id, title, description, cover_photo_id, date_start/end, photo_count, source (`auto`/`manual`) |
| `album_photos` | материализованные фото (album_id, photo_id) — статика: отдельные фото, фото персон/автоальбомов, состав автоальбомов |
| `album_members` | «семечки» — из чего собран ручной альбом: (album_id, member_type, member_id, member_label, photo_count) |

## Семечки (album_members)

| member_type | Природа | member_id |
|---|---|---|
| `photo` | материализованная (отдельное фото → album_photos) | photo UUID |
| `persona` | материализованная (фото персоны + её автоальбомы копируются в album_photos) | persona_id |
| `album` | материализованная (создаётся вместе с persona; фото автоальбома скопированы) | album_id |
| `catalog` | **ЖИВАЯ ССЫЛКА** — фото НЕ копируются в album_photos | `root_id\|path` |

## Семечка catalog (живая ссылка)

Принцип: добавить каталог ≠ собрать его содержимое. Семечка хранит только
`root_id|path`; состав вычисляется в момент чтения через
`DatabaseManager.get_catalog_photo_ids()` — все canonical, не удалённые, ingested
файлы папки и всех вложенных (по `parent_dir`, граница слэша — `2024` не захватывает `2024x`).

Актуальность обеспечивается существующей индексацией: pipeline сам поддерживает
`catalog_files` (`ingested`, `deleted`) в актуальном состоянии — альбом следует за ним без
какого-либо watcher'а. Новые проиндексированные фото появляются в альбоме сами;
удалённые с диска (deleted=1) — исчезают.

Резолвер встроен в `DatabaseManager.get_album_photos()` — единая точка: статика
(`album_photos`) + живые фото catalog-семечек, дедупликация по photo_id, сортировка
по дате. Все читатели через резолвер (основной API, share `s_get_album`, превью)
получают динамику автоматически. Исключение: share-список альбомов (`s_list_albums`)
собирается отдельным SQL по `album_photos` — там живые альбомы добираются отдельно
(те, чей резолверный состав пересекается со scope). `_update_album_meta` считает
photo_count/даты/обложку по полному составу; обложка сохраняется, если она ещё в составе.
`refresh_album_meta_if_catalog()` вызывается при чтении альбома/списка — мета не устаревает.

Ограничение: фото, пришедшее через каталог, нельзя пока удалить поштучно из альбома
(кнопка «Удалить фото из альбома» работает только с album_photos). Решение —
будущая сущность «исключение» (exclude-семечка), см. план ниже.

## План соответствия (на будущее, согласовано, не реализовано)

Динамический принцип — стандарт для ВСЕХ групповых сущностей:
- persona/album-семечки перевести на живой резолв (без копирования в album_photos);
- album_photos оставить только для отдельно стоящих фото и автоальбомов;
- сущность `exclude_photo` — материализованное исключение конкретного фото
  из динамического состава («отрицательная photo-семечка»);
- состав альбома = UNION(живые семечки) + photo-семечки − exclude-семечки.

## API

- `POST /api/albums/{id}/members` — добавить семечку (`member_type`, `member_id`);
  для catalog `member_id = "root_id|path"`, фото не копируются, 422 при неверном формате,
  404 при неизвестном root_id.
- `DELETE /api/albums/{id}/members/{type}/{member_id:path}` — удалить семечку;
  для catalog — просто удаление записи (чистить нечего), пересчёт мета.
  `member_id:path` — конвертер пути, т.к. catalog member_id содержит слэши.
- `GET /api/albums/{id}/members` — состав; photo_count catalog-семечек пересчитывается живьём.

## UI

- Каталог → выбор папки → detail-панель → кнопка «В альбом» → модалка: имеющийся
  ручной альбом или создание нового (название подставляется из имени папки).
- Страница Альбомы: catalog-семечка в строке «Состав:» с иконкой 📂 и живым счётчиком.
